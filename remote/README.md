# @northcinder/remote — optional self-hosted read-only MCP bridge

An optional bridge for a buyer or independent deployer who wants to expose ONLY the two
read-only tools — `search_products` (buyer's brief + interpretation echo + `rankingVerified`)
and `get_trust_signal` — over **Streamable HTTP**. The person using this package deploys and
operates it on infrastructure they control. The NorthCinder repository owner does not run a bridge,
publish a default endpoint, issue its keys, receive its traffic, or provide an operational service.

It exposes **no** purchase, approval, watch, profile, or order tools. Those stay in the local
stdio client (`@northcinder/client`) where the user's own keys, sessions, and the human approval
gate live. A test (`remote/test/mcp-server.test.ts`) asserts the checkout/approval/watch tools
are absent from `tools/list`.

## What it is (and isn't)

- **Thin proxy, not a second brain.** Every tool call re-runs `verifySearchRanking` over the
  deployer's engine inputs — the remote bridge does not trust the engine's ordering any
  more than the stdio client does; `rankingVerified` is computed here, on the bridge. The
  neutrality honesty travels to remote users unchanged.
- **No LLM calls.** Ranking + brief are deterministic composition (`@northcinder/protocol` +
  `@northcinder/brief`).
- **No checkout.** By construction — the tool surface is two read tools.

## Run it

```bash
pnpm --filter @northcinder/remote build
NORTHCINDER_REMOTE_API_KEYS="acme:<≥16-char-key>,globex:<≥16-char-key>" \
NORTHCINDER_SERVICE_URL="https://your-northcinder-engine.example" \
NORTHCINDER_SERVICE_KEY="<key you generated for your engine>" \
node remote/dist/main.js
# → [northcinder-remote] listening on http://0.0.0.0:8791 (MCP endpoint: /mcp, health: /health)
```

| Env | Required | Default | Meaning |
|---|---|---|---|
| `PORT` | no | `8791` | listen port |
| `NORTHCINDER_REMOTE_API_KEYS` | yes | — | keys generated by the deployer for this bridge: `clientId:key[,clientId:key…]` |
| `NORTHCINDER_SERVICE_URL` | yes | — | base HTTP(S) URL of the deployer's NorthCinder engine; URL userinfo is rejected (use `NORTHCINDER_SERVICE_KEY`) |
| `NORTHCINDER_SERVICE_KEY` | yes | — | key generated by the deployer for this bridge to call their engine |
| `NORTHCINDER_REMOTE_RATE_CAPACITY` | no | `30` | token-bucket capacity per client key |
| `NORTHCINDER_REMOTE_RATE_REFILL_PER_SEC` | no | `0.5` | refill/sec per client key (≈30/min) |

## Endpoints

- `POST /mcp` — the MCP Streamable HTTP endpoint. Requires `Authorization: Bearer <client key>`;
  missing/unknown key → structured `unauthorized` (401). Over the per-key token bucket →
  structured `rate_limited` (429) with a `Retry-After` header. Request bodies are capped at
  **1 MiB** (`MAX_MCP_BODY_BYTES` in `src/http-server.ts`) — a leaked client key can't be used
  to push unbounded bodies at the process; oversized bodies get a structured `payload_too_large`
  (413) before the MCP transport ever sees them. Auth runs before this cap is enforced (it only
  reads the header), so an unauthenticated oversized request still gets 401, not 413.
- `GET /health` — unauthenticated liveness: `{ ok: true, service: "northcinder-remote", version }`.

## Self-hosting

Runs on any Node ≥20 host (a VM, a container, a PaaS dyno). It is a **public-facing** service —
it binds `0.0.0.0` deliberately (unlike the local dashboard, which is loopback-only). Terminate
TLS in front of it (reverse proxy / platform), point `NORTHCINDER_SERVICE_URL` at your closed
engine, and generate each consumer surface its own `NORTHCINDER_REMOTE_API_KEYS` entry so you can rate-
limit and revoke per client. `GET /health` is your readiness/liveness probe.

**This repository does not deploy or operate this bridge.** Ship it with your own pipeline and
credentials. Your deployment creates no callback or control connection to the repository owner.

## Registry metadata

NorthCinder is not currently listed in the official MCP Registry. This repository does not include a
deployer-ready remote manifest because the bridge has no NorthCinder-operated URL to publish. A user who
deploys the bridge must create metadata for their own verified namespace and HTTPS endpoint, then validate it
against the current registry schema before submission. The local stdio package needs its own current,
package-linked metadata before the project maintainer submits it separately.
